### 问题 11:14 个 Controller 全部缺少 RBAC(角色越权)

**位置**:全部 14 个 controller

**现状**:全局 `JwtAuthGuard` 只校验"登录了",不校验"角色"。schema 定义了 `admin / manager / staff` 三种角色,但**代码里没有任何 `@Roles` 装饰器或 `RolesGuard`**。一个 `staff` 账号登录后,可以用 token 调用所有接口:删除用户、修改订单状态、删除租户数据,全部放行。

**问题**:
- staff 能删用户、改管理员密码
- staff 能确认入库、发货、对账回款(财务操作)
- staff 能访问 `/api/tenants` 看到所有租户信息(跨租户)
- 任何登录用户都能调 `/api/users` 拿到全员列表

**解法**:实现 RBAC 守卫
```ts
// src/common/decorators/roles.decorator.ts
import { SetMetadata } from '@nestjs/common';
export const ROLES_KEY = 'roles';
export const Roles = (...roles: string[]) => SetMetadata(ROLES_KEY, roles);

// src/common/guards/roles.guard.ts
@Injectable()
export class RolesGuard implements CanActivate {
  constructor(private reflector: Reflector) {}
  canActivate(context: ExecutionContext): boolean {
    const required = this.reflector.getAllAndOverride<string[]>(ROLES_KEY, [
      context.getHandler(), context.getClass(),
    ]);
    if (!required) return true;  // 不标 @Roles 的接口,登录即可
    const { user } = context.switchToHttp().getRequest();
    return required.includes(user.role);
  }
}
```
```ts
// app.module.ts 全局注册
{ provide: APP_GUARD, useClass: RolesGuard }

// 敏感接口标注
@Roles('admin')
@Delete(':id')
remove(...) { ... }
```

**工作量**:1-2 天(需要梳理每个接口的最小角色)。

### 问题 12:JWT 密钥硬编码兜底值,生产可被伪造 token

**位置**:`src/modules/auth/jwt.strategy.ts:17`

**现状**:
```ts
secretOrKey: process.env.JWT_SECRET || 'fastener-saas-secret-key',
```

**问题**:如果生产环境漏配 `JWT_SECRET`,会静默回退到硬编码值。攻击者知道这个值(代码可见),就能伪造任意用户的 token,完全绕过登录。这是个**静默的安全降级**——应用正常启动,但密钥强度为零。

**解法**:启动时强制校验,缺失直接报错退出
```ts
const secret = process.env.JWT_SECRET;
if (!secret || secret.length < 32) {
  throw new Error('JWT_SECRET 必须配置且长度至少 32 字符');
}
super({ jwtFromRequest: ..., ignoreExpiration: false, secretOrKey: secret });
```
> 同理 `DATABASE_URL` 等关键环境变量都应在启动时校验,缺了就 crash,而不是带着弱配置裸跑。

### 问题 13:异常 Filter 把 Prisma 错误信息原样返回给前端(信息泄漏)

**位置**:`src/common/filters/global-exception.filter.ts:47`

**现状**:
```ts
} else {
  httpStatus = HttpStatus.BAD_REQUEST;
  code = ErrorCode.BUSINESS_ERROR;
  message = exception.message;   // ❌ Prisma 原始错误信息直接给前端
}
```

**问题**:未识别的 Prisma 错误会把 `message` 原样返回。这类信息可能含表名、字段名、SQL 片段,帮攻击者了解数据库结构。例如外键约束错误会暴露 `order_items_orderId_fkey`,攻击者据此推断表关系。

**解法**:对未识别的 Prisma 错误,只返回通用提示,详情写日志
```ts
} else {
  httpStatus = HttpStatus.BAD_REQUEST;
  code = ErrorCode.BUSINESS_ERROR;
  message = '数据操作失败';
  this.logger.error(`Prisma error [${exception.code}]: ${exception.message}`, exception.stack);
}
```
> 同理 `exception instanceof Error` 分支也不要把 `message` 给前端(可能含文件路径、堆栈线索)。

### 问题 14:对账操作 `reconcile` 无事务,中途失败导致金额错乱

**位置**:`src/modules/settlement/settlement.service.ts` 的 `reconcile`

**现状**:循环里每次创建一条 `settlement`,循环结束后重算 `order.paidAmount`。**全部无事务**。如果循环到第 3 条时抛错,DB 里已经有前 2 条 settlement,但 `order.paidAmount` 还是旧值 → **已收款记录和订单 paidAmount 长期不一致**。

**问题**:对账是财务核心操作,部分失败直接导致账对不上。

**解法**:整批用事务包裹
```ts
await this.prisma.$transaction(async (tx) => {
  for (const item of dto.items) {
    const orderItem = await tx.orderItem.findFirst({ ... });
    // 余额校验
    const existing = await tx.settlement.findMany({ ... });
    if (alreadySettled + item.amount > itemTotal) throw ...;
    await tx.settlement.create({ data: { ... } });
  }
  // 重算 paidAmount
  const all = await tx.settlement.findMany({ where: { orderId, tenantId } });
  const paid = all.reduce((s, x) => s.plus(new Decimal(x.amount)), new Decimal(0));
  await tx.order.update({ where: { id: dto.orderId }, data: { paidAmount: paid } });
});
```
> 与第一轮问题 #2 同类,但这是最严重的实例之一——金额类操作必须事务。

### 问题 15:状态机不校验非法转换(数据进入不可达状态)

**位置**:多处 `updateStatus`

**现状**:
```ts
// order.service.ts
async updateStatus(id: number, status: string) {
  await this.db.order.updateMany({ where: { id, tenantId }, data: { status } as any });
}
// purchase.service.ts
async updateStatus(id: number, status: string) {
  await this.db.purchaseOrder.updateMany({ where: { id, tenantId }, data: { status } as any });
}
```

**问题**:
- 任意传 `status`,不校验是否合法。能从 `delivered` 改回 `pending`,从 `cancelled` 改成 `completed`
- `as any` 绕过类型,传 `status: "乱写"` 也能写进库(虽然 enum 会拒,但报错信息难看)
- 没有"只能从 X 转 Y"的转换矩阵
- quotation 有 `accept/reject/send` 的状态校验(写得好),但 order/purchase 的 `updateStatus` 没有

**解法**:状态转换矩阵 + 强类型
```ts
const ORDER_TRANSITIONS: Record<OrderStatus, OrderStatus[]> = {
  pending: ['partial_delivered', 'delivered', 'cancelled'],
  partial_delivered: ['delivered', 'cancelled'],
  delivered: ['completed'],
  completed: [],
  cancelled: [],
};

async updateStatus(id: number, next: OrderStatus) {
  const order = await this.findOne(id);
  if (!ORDER_TRANSITIONS[order.status].includes(next)) {
    throw new BadRequestException(`订单不能从 ${order.status} 转为 ${next}`);
  }
  await this.prisma.order.updateMany({ where: { id, tenantId }, data: { status: next } });
}
```
> DTO 里 `status` 字段也应改成 enum(`@IsEnum(OrderStatus)`),而非裸 string。

### 问题 16:报价转订单 库存扣减逻辑重复且有竞态

**位置**:`src/modules/quotation/quotation.service.ts` 的 `processOrderItems` (127-144 行)

**现状**:这里**复制了一份** order.service 的库存扣减代码,有同样竞态(第一轮问题 #1)。

**问题**:
1. 重复代码——两处都改才算修,容易漏
2. 同样竞态——报价接受时并发也会卖超

**解法**:抽取共享的库存扣减方法,两处复用
```ts
// src/modules/inventory/stock.service.ts(新建)
@Injectable()
export class StockService {
  constructor(private prisma: PrismaService) {}
  async deduct(tx: PrismaTransaction, skuId: number, tenantId: number, qty: number) {
    const r = await tx.sku.updateMany({
      where: { id: skuId, tenantId, stock: { gte: qty } },
      data: { stock: { decrement: qty } },
    });
    if (r.count === 0) throw new BadRequestException('库存不足');
    // 返回 source 标记
    return 'stock';
  }
}
```
> order.service 和 quotation.service 都注入 StockService 调用。配合第一轮问题 #2 的事务一起改。

### 问题 18:创建订单/报价时 SKU 查询串行(Promise.all 内含 await 仍逐条查)

**位置**:`order.service.ts` 的 `processItems`、`quotation.service.ts` 的 `processOrderItems`

**现状**:
```ts
return Promise.all(items.map(async (item) => {
  const sku = await this.db.sku.findFirst({ where: { id: item.skuId, tenantId } });
  // ...
}));
```

**问题**:`Promise.all` 看似并发,但每个分支里一次 `findFirst` 仍发一条 SQL,N 个条目 = N 次往返。订单 50 项 = 50 次查询。MySQL/PG 每次往返 ms 级,累加明显。

**解法**:先批量查所有 SKU,再内存匹配
```ts
const skuIds = items.map(i => i.skuId);
const skus = await this.prisma.sku.findMany({
  where: { id: { in: skuIds }, tenantId },
  include: { product: true },
});
const skuMap = new Map(skus.map(s => [s.id, s]));
for (const item of items) {
  const sku = skuMap.get(item.skuId);
  if (!sku) throw new BadRequestException(`SKU ${item.skuId} 不存在`);
  // ...处理
}
```

### 问题 19:全局异常 Filter 依赖 `response.status()` 但未校验是否 HTTP 上下文

**位置**:`global-exception.filter.ts:18-19`

**现状**:
```ts
const ctx = host.switchToHttp();
const response = ctx.getResponse();
// ...
response.status(httpStatus).json(...);
```

**问题**:`@Catch()` 捕获所有异常,包括非 HTTP 上下文(WebSocket、gRPC、定时任务)抛的。在非 HTTP 场景 `getResponse()` 不是 Express response,调用 `.status().json()` 会二次抛错,掩盖原始异常。

**解法**:判断类型
```ts
if (host.getType() !== 'http') {
  this.logger.error(exception);
  return;
}
const response = ctx.getResponse<Response>();
```

### 问题 20:PrismaService 无连接池配置,无重连/超时

**位置**:`src/prisma/prisma.service.ts`

**现状**:
```ts
const pool = new Pool({ connectionString: process.env.DATABASE_URL });
const adapter = new PrismaPg(pool);
super({ adapter });
```

**问题**:
- `Pool` 用默认参数,无 `max`/`idleTimeoutMillis`/`connectionTimeoutMillis`,高并发或 DB 抖动时表现不可控
- 无重连逻辑,DB 重启后连接池里的死连接不会自动清理(PG adapter 通常能自愈,但极端情况会卡)
- 没有 `enableShutdownHooks`,Nest 优雅关闭时 Prisma 可能没正确 disconnect(concurrent 请求被截断)

**解法**:
```ts
const pool = new Pool({
  connectionString: process.env.DATABASE_URL,
  max: 20,                    // 最大连接数,根据 PG max_connections 设
  idleTimeoutMillis: 30000,
  connectionTimeoutMillis: 5000,
});
super({ adapter });

async enableShutdownHooks(app: INestApplication) {
  process.on('beforeExit', async () => { await this.$disconnect(); });
}
```
> 主模块 onModuleDestroy 已 disconnect,但建议加 `enableShutdownHooks` 处理 SIGTERM。容器停止时 entrypoint 收到 SIGTERM,Nest 应优雅关闭正在处理的请求。

### 问题 21:全局响应有内存累积风险(无 Operator 类统计)

**位置**:**未发现**(这是个缺失项)

**现状**:项目里**没有任何**指标埋点:无请求数、无错误率、无慢查询、无 DB 连接池占用监控。生产出了问题只能看 docker logs,看不到"哪个接口慢""哪个错误频发"。

**解法**(分级实施):
1. 短期:接 Prometheus(`@willsoto/nestjs-prometheus`),暴露 `/metrics`,自动采集 HTTP 请求数/延迟/错误
2. 中期:加结构化日志(`nestjs-pino`),每条日志带 tenantId/requestId,出问题能查
3. 长期:接入阿里云 ARMS / SLS,日志和指标可视化

> 这是生产健壮性的"可观测性"维度。没有它,部署上线后是"黑盒"。

### 问题 22:`update` 接口透传 DTO 到 `updateMany`,可能写入非法字段

**位置**:多处
```ts
// customer / supplier / quotation 的 update
await this.db.xxx.updateMany({ where: { id, tenantId }, data: dto });
// user update
await this.prisma.user.updateMany({ where: { id, tenantId }, data });
```

**问题**:`data: dto` 直接透传,如果 DTO 里混入了 `id`、`tenantId`、`createdAt`,会被一起写进库。虽然 ValidationPipe 的 `whitelist: true` 拦了未知字段,但 DTO 里已声明的字段(如 UpdateUserDto 的 role)可能被越权修改。结合问题 11(无 RBAC),staff 可以通过 `PATCH /api/users/:id` 把自己提升为 admin(如果 UpdateUserDto 含 role 字段且无角色校验)。

**解法**:
- 敏感字段的更新单独接口 + 角色守卫(如改 role 必须 admin)
- DTO 用 `OmitType` 排除敏感字段,或拆分 `UpdateProfileDto` / `UpdateRoleDto`

### 问题 23:分页 pageSize 无上限,可一次拉全表

**位置**:所有 query DTO

**现状**:`pageSize` 默认 20,只有 `@Min(1)`,**没有 `@Max(100)`**。

**问题**:前端传 `pageSize=1000000` 一次拉出几十万行,DB 和内存都扛不住,等同 DoS。

**解法**:
```ts
@IsOptional() @IsInt() @Min(1) @Max(100) @Type(() => Number)
pageSize?: number = 20;
```
service 里再加兜底:`const size = Math.min(pageSize ?? 20, 100)`。

### 问题 24:`pageSize` 默认值在 DTO 和 service 里各写一遍,可能不一致

**位置**:DTO `pageSize?: number = 20` + service `const { pageSize = 20 } = query`

**问题**:两处默认值,改一处漏一处会产生 bug。已经是潜在不一致点。

### 问题 27:错误码体系未充分利用

**位置**:

**现状**:`error-codes.ts` 定义了 6 个错误码(0/1001/1002/1003/2001/9999),但 service 里抛异常时**不用错误码**,只抛 `BadRequestException('xxx')`。最终 filter 按 HTTP 状态码反推 code,粒度粗。

**问题**:"库存不足""订单状态非法""SKU 不存在"都被映射成同一个 `BUSINESS_ERROR = 2001`,前端无法据 code 做差异化处理(如库存不足弹补货,状态非法弹提示)。

**解法**:扩展错误码,业务异常带 code
```ts
export class BusinessException extends HttpException {
  constructor(public code: number, message: string, status = 400) {
    super({ code, message }, status);
  }
}
// 使用
throw new BusinessException(ErrorCode.STOCK_INSUFFICIENT, '库存不足');
```

### 问题 28:审计字段(operatorId)记录不完整

**位置**:`inbound.service.ts` 的 `create` 用了 `operatorId`,但 `order` / `purchase` / `quotation` / `settlement` 等表无操作人字段

**现状**:schema 里只有 `InboundOrder.operatorId` 一处关联 User。其他业务单据(订单、采购单、报价单、发货单、对账)都**没记录谁创建/修改**。

**问题**:工厂场景出问题要追责——"这张订单谁下的""对账谁回的款",没有操作人记录就无法追溯。`OrderRevision.beforeData/afterData` 也没存操作人。

**解法**:业务表加 `createdBy` / `updatedBy` 字段
```prisma
model Order {
  ...
  createdBy Int?
  updatedBy Int?
  user User? @relation("OrderCreator", fields: [createdBy], references: [id])
  updater User? @relation("OrderUpdater", fields: [updatedBy], references: [id])
}
```
service 里从 `tenantCtx.getUserId()` 注入。
