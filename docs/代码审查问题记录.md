## 二、问题清单(按严重度分级)

### 🔴 P0 — 数据正确性硬伤(生产前必修)

#### 问题 1:库存扣减存在并发竞态(读-判断-写非原子)

**位置**:`src/modules/order/order.service.ts` 的 `processItems` / `addItem`

**现状**:
```ts
const sku = await this.db.sku.findFirst({ where: { id, tenantId } });
if (sku.stock >= item.qty) {
  source = 'stock';
  await this.db.sku.update({
    where: { id: sku.id },
    data: { stock: sku.stock - item.qty },   // 基于读到的旧值算
  });
}
```

**问题**:两个请求同时读到 `stock=10`,都判断 `>=5`,都写入 `5`,实际应为 `0` —— **卖超库存**。1 家租户、2 个销售同时下同一 SKU 即可触发,不需要高并发。

**解法**(推荐):Prisma 原子操作 + 条件更新
```ts
const result = await this.prisma.sku.updateMany({
  where: { id, stock: { gte: qty } },   // 库存够才更新
  data: { stock: { decrement: qty } },   // 数据库层原子减
});
if (result.count === 0) throw new BadRequestException('库存不足');
```
对应 SQL:`UPDATE skus SET stock = stock - ? WHERE id = ? AND stock >= ?`,数据库行锁保证原子,多请求并发安全。

**替代解法**(需要返回更新后的值):原生 SQL + RETURNING
```ts
const [updated] = await this.prisma.$queryRaw`
  UPDATE skus SET stock = stock - ${qty}
  WHERE id = ${skuId} AND stock >= ${qty}
  RETURNING *
`;
```

**为什么不推荐分布式锁**:见附录《为什么不用分布式锁》。库存扣减是单库内的同资源竞态,数据库原子操作是最高效、最可靠、无外部依赖的解法。

#### 问题 2:多步业务操作无事务,部分失败留脏数据

**位置**:多个 service,涉及多步写操作但没有 `$transaction` 包裹

**典型场景**:

**2.1 入库确认 `inbound.service.ts` 的 `confirm`**(5 步无事务)
1. 更新采购单条目 `receivedQty`
2. 加权平均更新 SKU `costPrice` 和 `stock`
3. 回填定制件 `OrderItem.costPrice`
4. 入库单状态改 `confirmed`
5. 同步采购单状态 `received` / `partial_received`

若第 3 步抛错,前 2 步已提交,后 2 步未跑 → **库存加了、成本算了,但入库单还是 pending**,数据彻底不一致。

**2.2 创建订单 `order.service.ts` 的 `create`**
- `processItems` 内扣库存 + `order.create` 写订单/条目,无事务

**2.3 增加条目 `order.service.ts` 的 `addItem`**(4 步无事务)
- 扣库存 + 创建 OrderItem + 创建 OrderRevision + 重算 totalAmount

**2.4 删除条目 `order.service.ts` 的 `removeItem`**(4 步无事务)
- 还库存 + 删 OrderItem + 创建 OrderRevision + 重算 totalAmount
- 若删条目成功但 `recalculateTotal` 失败 → **总额与条目不匹配**

**2.5 发货 `delivery.service.ts` 的 `ship`**(3 步无事务)
- 更新 OrderItem `deliveredQty` + 改发货单状态 + 改订单状态

**解法**:Prisma 交互式事务包裹
```ts
await this.prisma.$transaction(async (tx) => {
  // 所有操作用 tx(事务客户端)而非 this.prisma
  await tx.sku.updateMany({ ... });
  await tx.orderItem.create({ ... });
  await tx.orderRevision.create({ ... });
  await tx.order.update({ ... });
  // 任意一步抛错,全部回滚
});
```

**注意事项**:
- 事务内不要混入外部调用(HTTP、发邮件、写文件),事务应尽量短
- 事务内查询也要用 `tx`,否则读不到未提交的中间状态
- 长事务会持锁影响并发,把无关查询放事务外

### 🟠 P1 — 并发正确性(数据量起来前必修)

#### 问题 3:单号生成器并发竞态

**位置**:`src/common/utils/no-generator.ts`

**现状**:
```ts
const records = await model.findMany({
  where: { tenantId, [field]: { startsWith: prefixWithDate } },
  orderBy: { [field]: 'desc' },
  take: 1,
});
// 解析最大序号 + 1,拼新单号
```

**问题**:两个请求同时查到最大序号是 5,都生成 `006`,插入时第二个因 `@unique` 报错。同一天两个销售同时建单即触发。

**解法 A**(推荐ustry):独立序列表 + 行锁
```prisma
model Sequence {
  id        Int @id @default(autoincrement())
  tenantId  Int
  prefix    String
  dateStr   String
  seq       Int @default(0)
  @@unique([tenantId, prefix, dateStr])
}
```
```ts
const seq = await this.prisma.$transaction(async (tx) => {
  const row = await tx.sequence.upsert({
    where: { tenantId_prefix_dateStr: { tenantId, prefix, dateStr } },
    update: { seq: { increment: 1 } },
    create: { tenantId, prefix, dateStr, seq: 1 },
  });
  return row.seq;
});
const orderNo = `${prefix}-${dateStr}-${String(seq).padStart(3, '0')}`;
```

**解法 B**(业界主流):放弃连续号,用 ULID/雪花算法
```ts
import { ulid } from 'ulid';
const orderNo = `SO-${dateStr}-${ulid().slice(-6)}`;
```
优点:无需查库、天然唯一、不暴露业务量。缺点:单号不再连续(真实生产订单号通常本就不连续)。

**解法 C**(简单但糙):捕获 unique 冲突重试
```ts
for (let i = 0; i < 3; i++) {
  try {
    return await this.prisma.order.create({ data: { orderNo: ... } });
  } catch (e) {
    if (e.code === 'P2002') continue;  // unique 冲突重试
    throw e;
  }
}
```

> 推荐解法 A(保留可读连续号)或解法 B(业界主流思路)。

#### 问题 4:缺索引(性能瓶颈)

**位置**:`src/prisma/schema.prisma`

**现状**:几乎无二级索引,只有 `@unique` 和主键。所有按 `tenantId` 过滤的查询都是全表扫描。

**问题**:订单/订单条目表过 10 万行后,`WHERE tenantId = ? ORDER BY createdAt DESC` 慢到秒级。

**解法**:给所有 `tenantId` + 高频查询字段加复合索引
```prisma
model Order {
  ...
  @@index([tenantId, createdAt])        // 列表分页排序
  @@index([tenantId, status])           // 按状态筛选
  @@index([tenantId, customerId])       // 按客户筛选
}

model OrderItem {
  ...
  @@index([tenantId, orderId])
  @@index([tenantId, skuCode])
}

model Sku {
  ...
  @@index([tenantId, skuCode])
}
// 其他业务表同理:tenantId + 高频过滤/排序字段
```
改动极小,Prisma migrate 后自动建索引,收益巨大。

### 🟡 P2 — 正确性与安全(应修)

#### 问题 5:登录查询效率与正确性问题

**位置**:`src/modules/auth/auth.service.ts` 的 `login`

**现状**:
```ts
const users = await this.prisma.user.findMany({ where: { username: dto.username } });
for (const user of users) {
  if (await bcrypt.compare(dto.password, user.password)) { ... }  // 遍历 bcrypt 比对
}
```

**问题**:
1. `username` 只 `@@unique([tenantId, username])` 不全局唯一,同名跨租户查出多条
2. `for` 循环逐个 `bcrypt.compare` —— **bcrypt 故意慢(约 100ms)**,遍历 N 个就是 N×100ms,登录延迟放大

**解法**:登录需带 tenantId 精确查一条,再比对一次
```ts
const user = await this.prisma.user.findFirst({
  where: { tenantId: dto.tenantId, username: dto.username },
});
if (!user) throw new UnauthorizedException('用户名或密码错误');
const ok = await bcrypt.compare(dto.password, user.password);
if (!ok) throw new UnauthorizedException('用户名或密码错误');
```
> 注意:LoginDto 需新增 `tenantId` 字段;或登录接口先按租户标识(域名/租户码)解析 tenantId。

#### 问题 6:类型安全形同虚设

**位置**:多处 service

**现状**:
```ts
private get db(): any { return this.prisma; }   // 多处用 any 代理
// 大量 as any
const totalAmount = items.reduce((sum, i) => sum + Number(i.price) * i.qty, 0);
await this.db.order.updateMany({ where: { id, tenantId }, data: { status } as any });
```

**问题**:`any` 让 TS 类型检查失效,等于退回 JS,重构时编译器帮不上忙,运行时才报错。

**解法**:
1. 删除 `private get db(): any`,直接用 `this.prisma`(Prisma Client 本身类型完整)
2. 去掉 `as any`,补全类型:
   - `status: string` → `status: OrderStatus`
   - DTO 的 `status` 字段用 enum 类型而非 string
3. 用 `satisfies` 替代 `as` 做类型检查

#### 问题 7:Decimal 运算精度风险

**位置**:`order.service.ts` 的 `recalculateTotal` / `create` 等

**现状**:
```ts
const totalAmount = items.reduce((sum, i) => sum + Number(i.price) * i.qty, 0);
```

**问题**:`Number(Decimal)` 转 JS 浮点后累加,可能丢精度。虽末尾 `Math.round(x*100)/100` 兜底,但中间过程已不准,财务对账可能"差几分钱"。

**解法**:用 `decimal.js` 或 Prisma 的 Decimal 方法做高精度运算
```ts
import { Decimal } from '@prisma/client/runtime/library';
const total = items.reduce(
  (sum, i) => sum.plus(new Decimal(i.price).times(i.qty)),
  new Decimal(0),
);
const totalAmount = Number(total.toDecimalPlaces(2));
```

## 附录:为什么不用分布式锁解决并发问题

### 分布式锁解决的真问题
协调**多个独立服务实例**之间的互斥资源(如多台 NestJS 跑定时任务去重、跨实例防重复支付、调用外部限频 API、跨微服务事务编排)。

### 为什么本项目不适用
1. **场景不存在**:1 台服务器、1 个 PG 容器、1 家租户,根本不"分布式"
2. **对症错误**:竞态问题(库存)用数据库原子操作更优;原子性问题(多步操作)用事务解决。锁管"谁先执行",事务管"全成全败",两回事
3. **副作用大**:把并发串行化降低吞吐;引入新故障点(Redis 挂了?锁过期?Redlock 争议);增加运维复杂度

### 决策树:遇到并发问题怎么选
```
同一资源并发修改?(库存、计数、单号)
├─ 是 → 数据库原子操作(updateMany + 条件 + decrement)
│        或原生 SQL UPDATE...WHERE...RETURNING
│        ❌ 不用锁
└─ 否,多步操作要全成全败?
├─ 是 → 数据库事务($transaction)
│        ❌ 不用锁
└─ 否,多个服务实例协调?
├─ 是 → 才考虑分布式锁(Redis Redlock)
└─ 否,单实例内临时互斥?
    → 本地内存锁(Node mutex / 队列)
       ❌ 不用分布式锁
```

### 核心观念
数据库本身就是完美的并发控制器:行级锁、MVCC、隔离级别、唯一约束、序列,都是为解决这类问题设计的。**能下沉到数据库就下沉,不要在应用层再叠一层锁。** 锁(本地或分布式)是"绕过数据库"时的无奈选择,不是首选。

| 方案 | 适用 | 本项目 |
|------|------|--------|
| 数据库原子操作 | 同资源并发修改 | ✅ 用(库存、计数) |
| 数据库事务 | 多步操作原子性 | ✅ 用(入库、下单) |
| 数据库唯一约束 | 防重复 | ✅ 用(单号、用户名) |
| 数据库序列 / ULID | 编号生成 | ✅ 用(单号) |
| 本地内存锁 | 单实例临时互斥 | ⚪ 暂不需要 |
| 分布式锁 | 多实例协调 | ❌ 不要用 |

## 重构路径建议

1. **第一步**:把 P0 两条(库存原子化 + 加事务)一起改 —— 因为改事务时顺带就触到库存扣减,合并改最省事
2. **第二步**:P1 两条(单号 + 索引) —— 单号改了再改业务,索引独立加
3. **第三步**:P2 三条(登录/类型/精度) —— 代码质量提升,无功能变更
4. **第四步**:P3 三条 —— 运维加固,可与部署收尾合并

> 改完 P0+P1,项目达到"生产可用"基线。P2/P3 是锦上添花。
