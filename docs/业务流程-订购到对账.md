# 紧固件 SaaS — 业务流程重构方案(订购 → 对账)

> 2026-07-08 基于实际业务流程的完整数据模型重构方案。
> 起因:现有订单模型(`Order + OrderItem.source='custom' + 一张 PurchaseOrder`)无法支撑真实业务——客户先发订购单、多轮议价、定制件的多道工序流转(进料→车加工→滚丝→铣床→磨床→钻床→热处理→表面处理)、分批发货。
> 本文只给方案,不动代码,作为后续重构的设计依据。

---

## 一、业务流程全景

### 1.1 原始业务描述

```
① 客户发起订购单
② 商户根据订购单报价
③ 客户考虑是否接受
④ 不接受 → 商户修改报价单,循环直到满意
⑤ 判定采购单上的商品:仓库都有且无特殊定制?
   ├─ 是 → 直接发货
   └─ 否 → 走定制采购流程(买原料→车加工→打丝等)
⑥ 定制完成后走发货流程(可能分批)
⑦ 对账结算
```

### 1.2 流程全景图

```
┌─────────────────────────────────────────────────────────────┐
│  ① 客户发订购单 PurchaseRequest (pending)                    │
└──────────────────────────┬──────────────────────────────────┘
                           ↓
┌─────────────────────────────────────────────────────────────┐
│  ② 商户报价 Quotation v1 (draft → sent)                      │
└──────────────────────────┬──────────────────────────────────┘
                           ↓
                  ③ 客户决策
              ┌────────────┴────────────┐
              ↓ 接受                    ↓ 不接受
┌─────────────────────────┐   ┌─────────────────────────────┐
│ Quotation→accepted       │   │ Quotation→rejected          │
│ PurchaseRequest→accepted │   │ 商户改 → Quotation v2 ──┐    │
│ 生成 Order              │   │ (循环直到客户接受)        │    │
└──────────┬──────────────┘   └─────────────────────────────┘
           ↓
┌─────────────────────────────────────────────────────────────┐
│  ④ Order 落单,逐条目判定 source                              │
│     仓库有现货且够 → source=stock                            │
│     否则           → source=custom                          │
│     Order 状态:accepted                                      │
└──────────────────────────┬──────────────────────────────────┘
                           ↓
        ⑤ 整单判定:全部现货且库存够?
        ┌────────────┴────────────┐
        ↓ 是                       ↓ 否(有定制件)
┌─────────────────────┐   ┌─────────────────────────────────┐
│ Order→ready_to_ship │   │ Order→sourcing/producing         │
│ 直接进入发货         │   │                                  │
└──────────┬──────────┘   │ ⑥ 定制流程(每条目一张生产工单)   │
           │              │                                   │
           │              │ ProductionOrder                   │
           │              │   工序链:进料→车→滚丝→铣→磨→   │
           │              │            钻→热处理→表面处理      │
           │              │   (按件选配子集,顺序固定)         │
           │              │                                   │
           │              │ 工序逐道完成 → 产出转可发货        │
           │              └──────────────┬───────────────────┘
           │                             ↓
           ↓                    Order→ready_to_ship
┌─────────────────────────────────────────────────────────────┐
│  ⑦ 发货(可分批)DeliveryOrder #1, #2, ...                   │
│     现货件:库存够就可发                                      │
│     定制件:工序完工量 >= 本次发货量才可发                    │
│     Order: ready_to_ship → partial_delivered → delivered     │
└──────────────────────────┬──────────────────────────────────┘
                           ↓
┌─────────────────────────────────────────────────────────────┐
│  ⑧ 对账 Settlement                                           │
│     按条目收款,paidAmount 累加                                │
│     收齐 → Order→completed                                  │
└─────────────────────────────────────────────────────────────┘
```

## 二、现有模型的 5 个核心 gap

| # | 实际流程 | 现有 schema | gap |
|---|---------|------------|-----|
| 1 | 客户先发订购单 | 无,从 Quotation 起 | 缺客户需求入口 |
| 2 | 报价多轮修改 | Quotation reject 后"死"了 | reject 后不能出新版,无版本沿革 |
| 3 | 定制=多道工序 | `source='custom'` + 一张 PurchaseOrder | **丢了工序流转**,采购单语义被滥用 |
| 4 | 现货够直发,否则先进生产 | 下单时一次性定 stock/custom | 库存判定应动态,定制件要等工序 |
| 5 | 分批发货 | DeliveryOrder 一次快照 | 缺"可发货量"概念,定制件分批无依据 |

## 三、核心概念:Order 与 OrderItem 的关系

### 3.1 一句话区别

**Order 是"一张合同",OrderItem 是"合同里的一行"。** 一份订单 = 1 个 Order + N 个 OrderItem。

### 3.2 为什么要拆

1. **每行要被独立引用**:生产工单、采购单、发货明细、对账都指向具体的行(`orderItemId`),JSON 没有稳定主键无法被外键引用
2. **每行有独立状态**:`qty`/`deliveredQty`/`source`/`costPrice` 属于行,不属于整张单
3. **行可独立增删改**:客户下单后说"这行加 50 个/这行取消",`OrderRevision` 留痕靠行独立存在

### 3.3 各自承担什么

| 放 Order(整单共享) | 放 OrderItem(各行可能不同) |
|--------------------|---------------------------|
| orderNo / customerId | skuCode / productName |
| quotationId / purchaseRequestId | qty / deliveredQty |
| totalAmount / paidAmount | price / costPrice |
| status(整单状态机) | source(stock/custom) |
| createdAt | purchaseOrderId?(直接采购时) |

**判定准则**:整张单所有行都一样 → Order;不同行可能不同 → OrderItem。

### 3.4 关联方式

外键只在子表存:`OrderItem.orderId` 指向 `Order.id`。Prisma 的 `Order.items: OrderItem[]` 是反向访问器,非真字段。所有其他单据的关联都是这个模式:子表存父表主键、`@relation` 声明关系、查询时 include 或 where。

## 四、模型清单(完整字段)

> 带 ★ 的是新增或改造字段。所有表统一带 `tenantId`(多租户铁律)。

### 4.1 PurchaseRequest — 订购单 ★ 新增

客户原始需求入口,在最前端。

```
PurchaseRequest
  id, tenantId ★
  requestNo          "PR-20260708-001"
  customerId         客户
  status             pending / quoting / quoted / accepted / rejected / cancelled
  expectedDate       客户期望交期
  remark             客户特殊要求/用途
  createdAt

PurchaseRequestItem
  id, tenantId ★
  purchaseRequestId  ★ 关联订购单
  productName        客户原始描述(可能还没建 SKU)
  specText           规格材质长度的裸文本
  attributes Json?   结构化属性(规格/材质/表面处理)
  qty                需求数量
  targetPrice?       客户期望单价(议价锚点)
  skuId?             商户后期匹配的 SKU(可空——客户要的可能要新建档)
```

**设计要点**:`skuId` 可空,处理"客户要的东西系统里没有"的真实场景——商户先建档再回填。

---

### 4.2 Quotation — 报价单 ★ 支持多版本

```
Quotation
  id, tenantId
  quotationNo        "BJ-20260708-001"
  purchaseRequestId  ★ 关联订购单(N 个版本属于同一订购单)
  version            ★ v1, v2, v3...
  customerId
  totalAmount
  validUntil
  status             draft / sent / accepted / rejected / superseded ★
  items              报价明细(可保留 Json 或拆 QuotationItem 表)
  createdAt

★ 唯一约束:[purchaseRequestId, version]
```

**多版本流转**:
```
Quotation v1(sent → rejected) ── 商户改 ──┐
Quotation v1 → superseded                  │
Quotation v2(draft → sent → ?) ◄───────────┘
  ↓ 若 v2 也被拒,出 v3,直到某版 accepted
  ↓ 接受
Quotation vN(accepted) → 生成 Order
```

`superseded` 表示"被自己新版取代",区别于 `rejected`(客户拒绝)。

---

### 4.3 Order — 订单 ★ 状态机重设

```
Order
  id, tenantId
  orderNo            "SO-20260708-001"
  purchaseRequestId  ★ 冗余外键,方便直接查
  quotationId        ★ 关联被接受的报价单
  customerId
  totalAmount
  paidAmount
  status             ★ 重设状态机(见下)
  createdAt
```

**订单状态机**:
```
accepted         报价刚被接受,落单
   ↓
sourcing         有定制件,开始采购原料(无定制则跳过)
   ↓
producing        定制件加工中
   ↓
ready_to_ship    全部就绪,可发货
   ↓
partial_delivered 部分发货
   ↓
delivered        全部发货
   ↓
completed        收款齐(对账联动)
   ↘ cancelled(任何阶段可取消,需回滚库存)
```

**状态自动推进规则**(不靠手动点):
| 触发动作 | 状态变化 |
|---------|---------|
| 报价 accepted,创建 Order | → accepted |
| 第一张定制件生产工单/采购单创建 | → sourcing/producing |
| 所有定制件工序完成 + 现货齐 | → ready_to_ship |
| 第一张 DeliveryOrder.shipped | → partial_delivered |
| 所有 OrderItem.deliveredQty=qty | → delivered |
| paidAmount=totalAmount | → completed |

---

### 4.4 OrderItem — 订单条目 ★ 现有,小改

```
OrderItem
  id, tenantId
  orderId             关联订单 ★ 现有
  productName
  skuCode
  skuAttrs Json?
  price               这行单价
  qty                 这行要多少
  deliveredQty        这行已发多少 ★ 现有
  source              stock / custom ★ 现有
  costPrice           这行成本 ★ 现有
  purchaseOrderId?    直接采购成品时关联 ★ 现有
```

**关系网枢纽**:上游接 Order,下游被 ProductionOrder/DeliveryItem/Settlement 引用(都通过 `orderItemId`)。

---

### 4.5 ProductionOrder — 生产工单 ★ 新增(核心)

每个定制条目的生产项目。

```
ProductionOrder
  id, tenantId ★
  productionNo        "MO-20260708-001"
  orderItemId         ★ 关联定制 OrderItem(唯一,1:1)
  qty                 投产数量(= OrderItem.qty)
  completedQty        已完工数量(最后一道工序通过的量)
  status              planning / in_progress / partial_done / done / cancelled
  plannedFinishDate   计划完工日
  createdAt

★ 唯一约束:[orderItemId]  一个定制条目只有一张工单
```

**设计要点**:
- 1:1 关联 OrderItem,每个定制件独立追踪进度
- `completedQty` 决定可发货量
- 产出**不进 Sku.stock**,避免定制件被当现货串货

---

### 4.6 ProcessStep — 工序 ★ 新增(核心)

生产工单内的工序链。详见第五章"工序设计"。

```
ProcessStep
  id, tenantId ★
  productionOrderId  ★ 关联生产工单
  sequence           顺序号(按实际走的排)
  stage              阶段:备料/成型/螺纹/后处理 ★
  stepType           枚举:进料/车加工/铣床/磨床/钻床/滚丝/热处理/表面处理
  name               工序名
  type               self(自制) / outsource(外协) ★
  supplierId?        外协供应商
  purchaseOrderId?   ★ 若需采购/外协,关联 PurchaseOrder
  surfaceMethod?     ★ 表面处理专用:镀锌/镀彩/达克罗/热镀锌
  status             pending / in_progress / done / skipped
  plannedQty         计划投入量
  actualQty          实际产出量
  lossQty            损耗量 ★
  dependsOnStepIds?  前置依赖工序(阶段内并行用)
  startedAt / completedAt
  remark
```

---

### 4.7 PurchaseOrder — 采购单 ★ 定位收窄

向供应商买现成东西,三种用途。

```
PurchaseOrder
  id, tenantId
  purchaseNo         "PO-20260708-001"
  supplierId         供应商
  totalAmount
  status             pending / confirmed / partial_received / received / cancelled
  expectedDate
  
  ★ 新增:
  purpose            material(原料) / outsource(外协) / finished_goods(成品采购)
  orderItemId?       ★ 成品采购时,关联 OrderItem
  processStepId?     ★ 原料/外协时,关联某道工序
  productionOrderId? ★ 冗余,方便查"这张工单的所有采购"
  
  ★ 约束:orderItemId 和 processStepId 至少一个非空
```

**三种身份**:
| purpose | 关联 | 业务含义 |
|---------|------|---------|
| material | processStepId(进料工序) | 给某定制件买原料 |
| outsource | processStepId(车/铣/磨/钻/热处理/表面处理) | 外协加工 |
| finished_goods | orderItemId | 订单直接买成品替代 |

---

### 4.8 DeliveryOrder + DeliveryItem — 发货单 ★ 增强校验

```
DeliveryOrder
  id, tenantId
  deliveryNo         "DO-20260708-001"
  orderId            关联订单(整单维度)
  logisticsCompany
  trackingNo
  status             pending / shipped / signed
  createdAt

DeliveryItem
  id, tenantId
  deliveryOrderId    关联发货单
  orderItemId        ★ 关联订单条目(这批发的是哪行)
  qty                本次发货数量
```

**分批发货机制**:
```
Order(qty=100, 现货60 + 定制40)
  ├─ DeliveryOrder #1(先发现货 60)→ Order: partial_delivered
  └─ DeliveryOrder #2(定制完工后发 40)→ Order: delivered
```

**可发货量校验**:
- 现货件:可发量 = `OrderItem.qty - deliveredQty`(受库存约束)
- 定制件:可发量 = `ProductionOrder.completedQty - 已通过 DeliveryItem 发的累计量`

发货时校验 `本次发货量 <= 可发量`,并发用条件更新防超发。

---

### 4.9 Settlement — 对账(现有,补联动)

```
Settlement
  id, tenantId
  orderId            关联订单
  orderItemId        关联条目(按行收款)
  amount             本次收款
  paidAt
  status             pending / paid
```

**对账联动订单状态**(第四轮 #44 修复):收款后若 `paidAmount >= totalAmount`,订单自动 `→ completed`。

## 五、工序设计(定制件加工流程)

### 5.1 工序链结构化

你的 8 道工序按加工性质是 **4 个阶段**:

```
阶段1:备料
  └─ 进料(买原料,钢厂/线材的盘条或棒料)

阶段2:成型加工(原料→毛坯→形状)
  ├─ 车加工(车床,车外圆/端面,针对非标件)
  ├─ 铣床(铣平面/槽)
  ├─ 磨床(高精度磨削)
  └─ 钻床(钻孔)

阶段3:螺纹加工
  └─ 滚丝(搓/滚螺纹,标准件这道为主)

阶段4:后处理(改变性能或表面)
  ├─ 热处理(调质/淬火,改变硬度强度)
  └─ 表面处理(镀锌/镀彩/达克罗/热镀锌,防锈装饰)
```

### 5.2 两个核心特征

**特征 1:固定顺序,但有分支/跳过**

每件不全部走 8 道,按件型选子集,但**阶段间顺序固定**(绝不先滚丝再车加工,绝不先表面处理再热处理):

| 件型 | 工艺路线 |
|------|---------|
| 标准件 M8 螺栓(碳钢) | 进料 → 滚丝 → 热处理 → 镀锌 |
| 非标台阶螺栓 | 进料 → 车加工 → 滚丝 → 热处理 → 达克罗 |
| 异形钻孔件 | 进料 → 车加工 → 钻床 → 滚丝 → 热处理 → 镀彩 |
| 高精度件 | 进料 → 车加工 → 磨床 → 滚丝 → 热处理 → 表面处理 |
| 小件不需热处理 | 进料 → 滚丝 → 镀锌 |

**特征 2:阶段 2 的 4 道加工可多道并用且顺序不定**

车/铣/磨/钻不互斥,一件可能又车又钻又磨。阶段 2 内部并行或顺序不定,但阶段 1→2→3→4 严格顺序。

### 5.3 推荐设计:顺序号 + 工序类型枚举 + 阶段标记

用 `sequence` 顺序号编排实际要走的工序,`stage` 标记阶段,`stepType` 标记具体工序,跳过的不建:

```
某非标台阶螺栓(车+滚丝+热处理+达克罗)的工序链:

PROD-ID  SEQ  STAGE      STEPTYPE    TYPE      STATUS
──────────────────────────────────────────────────────────
工单MO1   1   备料       进料        outsource done     →PurchaseOrder(原料)
工单MO1   2   成型       车加工      outsource done     →PurchaseOrder(外协车)
工单MO1   3   螺纹       滚丝        self      done
工单MO1   4   后处理     热处理      outsource done     →PurchaseOrder(外协热处理)
工单MO1   5   后处理     表面处理    outsource in_progress →PurchaseOrder(外协达克罗)
                                                      surfaceMethod=达克罗
```

**为什么不用固定 8 道全建、用 skipped 跳过?**
- 大部分件只走 3-4 道,建 8 道其中 4 道 skipped 是噪音
- 查询"这个工单有哪些真要做的事"要过滤 skipped,累
- 顺序号直接反映真实工艺,排产、外协、成本都对得上

**阶段 2 内部顺序怎么处理?**
- 简单做法:按 `sequence` 排,工艺员建工单时按实际加工顺序排好(车→钻→磨)
- 进阶做法:用 `dependsOnStepIds` 字段表达依赖,允许车和钻并行,磨等它们都 done。但紧固件多为流水线,顺序号足够,先不上依赖图

### 5.4 工序流转机制

```
ProductionOrder(MO-001, qty=100) 创建时 status=planning
  ↓ 按工艺模板生成工序链
工序按 sequence 逐道推进:
  工序1 必须先做,后续工序依赖前道 done(且产出量 known)
  产出量按损耗递减:工序2投入 = 工序1产出;工序3投入 = 工序2产出 - 损耗

每道工序:
  是 buy_material/outsource → 创建 PurchaseOrder
  采购/外协到货 → 工序入库 → 工序 status=done
  
最后道工序 done → ProductionOrder.completedQty 更新
  → completedQty 这批料转入"可发货"(不进通用库存)
全部工单 done + 现货齐 → Order → ready_to_ship
```

### 5.5 工艺模板(可选,A+ 阶段)

按 SKU/品类预置标准工序序列,建工单时一键带入再调整:

```
ProcessTemplate
  id, tenantId, name "标准螺栓工艺", categoryId/skuId
  
ProcessTemplateStep
  templateId, sequence, stage, stepType, name, type, defaultSurfaceMethod?
```

建生产工单时选模板,自动生成工序链。A 阶段可手工编排每道工序,A+ 再做模板。

## 六、完整关联图

```
PurchaseRequest ──1:N──→ Quotation(v1/v2/...)
       │                          │
       │                          │ (被接受的版本)
       │                          ↓
       └──→ Order ←───────────────┘
              │
              ├─ 1:N → OrderItem(订单明细行)
              │           │
              │           ├─ 1:1 → ProductionOrder(定制件生产工单)
              │           │           │
              │           │           └─ 1:N → ProcessStep(工序链)
              │           │                       │
              │           │                       └─ N:1 → PurchaseOrder(工序采购)
              │           │
              │           ├─ 1:N → DeliveryItem(这行发了多少)← 属于 DeliveryOrder
              │           │
              │           └─ 1:N → Settlement(这行收了多少)
              │
              ├─ 1:N → DeliveryOrder(发货单,整单维度)
              │           └─ 1:N → DeliveryItem(明细回指 OrderItem)
              │
              └─ 1:N → Settlement(对账,整单+行级双指)

PurchaseOrder(purpose=finished_goods) 直接关联 OrderItem
```

### 6.1 关联层级总结

| 单据 | 关联字段 | 指向 | 模式 |
|------|---------|------|------|
| Quotation | `purchaseRequestId` | PurchaseRequest | 因果链 |
| Order | `purchaseRequestId`, `quotationId` | 购/报价 | 冗余外键 |
| OrderItem | `orderId` | Order | 主从 |
| ProductionOrder | `orderItemId`(唯一) | OrderItem | 1:1 |
| ProcessStep | `productionOrderId` | ProductionOrder | 工单内 |
| PurchaseOrder | `orderItemId?` + `processStepId?`(二选一) | OrderItem 或 ProcessStep | 双身份 |
| DeliveryOrder | `orderId` | Order | 整单 |
| DeliveryItem | `deliveryOrderId` + `orderItemId` | 发货单 + 条目 | 双指 |
| Settlement | `orderId` + `orderItemId` | Order + 条目 | 双指 |

### 6.2 关联设计原则

**外键关联不是"为了关联而关联",每个关联背后是一个业务问题。** 按这个顺序设计:
1. 运营会问什么问题?(这单定制到哪了/涉及哪些采购/客户下过哪些单)
2. 这个问题从哪个单据出发,join 到哪?
3. 为了这个 join,谁该存谁的外键?

## 七、三层数据流详解

### 7.1 第一层:从客户需求到订单成型(步骤 ①②③④)

```
PurchaseRequest(pending)
    ↓ 商户基于它报价
Quotation v1(draft → sent)
    ↓ 客户拒绝
Quotation v1(rejected) → 商户改 → Quotation v2(draft → sent)
    ↓ 客户接受
Quotation v2(accepted), PurchaseRequest(accepted)
    ↓ 自动生成
Order(accepted) + OrderItem[]
    ↓ 逐条目判定 source
每个 OrderItem: 仓库现货够 → source=stock
                否则       → source=custom
```

### 7.2 第二层:备货与定制(步骤 ⑤⑥)

```
Order(accepted) 判定:
  全部 source=stock 且库存够 → ready_to_ship(跳过生产)
  有 source=custom → sourcing/producing

对每个 custom 的 OrderItem:
  创建 ProductionOrder(planning → in_progress)
  按工艺生成 ProcessStep 链:
    进料 → 车 → 滚丝 → 铣 → 磨 → 钻 → 热处理 → 表面处理
    (按件选配子集,顺序固定)

每道工序:
  buy_material → 创建 PurchaseOrder(purpose=material)
  outsource    → 创建 PurchaseOrder(purpose=outsource)
  self         → 仅记状态时间
  采购/外协到货 → 工序入库 → 工序 status=done

全部工序 done → ProductionOrder.done, completedQty 更新
全部定制工单 done + 现货齐 → Order → ready_to_ship
```

### 7.3 第三层:发货与结算(步骤 ⑦⑧)

```
Order(ready_to_ship)
    ↓ 发货(可分批)
DeliveryOrder #1 → shipped → Order(partial_delivered)
    ↓ 继续发
DeliveryOrder #2 → shipped → Order(delivered)
    ↓ 客户签收
DeliveryOrder → signed
    ↓ 对账收款(可分次)
Settlement #1 → Order.paidAmount 累加
    ↓ 收齐
paidAmount = totalAmount → Order(completed)
```

## 八、状态机汇总

| 单据 | 状态流转 |
|------|---------|
| PurchaseRequest | pending → quoting → quoted → accepted / rejected / cancelled |
| Quotation | draft → sent → accepted / rejected / superseded |
| Order | accepted → sourcing → producing → ready_to_ship → partial_delivered → delivered → completed / cancelled |
| ProductionOrder | planning → in_progress → partial_done → done / cancelled |
| ProcessStep | pending → in_progress → done / skipped |
| PurchaseOrder | pending → confirmed → partial_received → received / cancelled |
| DeliveryOrder | pending → shipped → signed |

## 九、关键设计决策

| 决策 | 选择 | 理由 |
|------|------|------|
| 订购单是否独立 | 独立 PurchaseRequest | 承接客户原始需求和议价锚点,几轮报价后仍可追溯 |
| 多轮报价用单表版本还是多张 | 多张 Quotation + version | reject 后能自然重生,每版独立单据号,审计清晰 |
| 定制件用 PurchaseOrder 还是新模型 | 新建 ProductionOrder + ProcessStep | 采购是"买现成",生产是"流转变出来",多道工序多供应商采购单表达不了 |
| 生产工单挂 Order 还是 OrderItem | 挂 OrderItem(1:1) | 同张订单多个定制件进度独立 |
| 工序用全部8道skipped还是按需建 | 按需建(sequence 顺序号) | 大部分件只走3-4道,全建噪音大查询累 |
| 工序采购关联到哪 | 关联 ProcessStep | 工序是采购的真正发起方,归属清晰 |
| 定制产出进不进 Sku.stock | 不进,用 ProductionOrder.completedQty | 定制件专属给订单,避免串货 |
| 现货+定制混合怎么处理 | OrderItem 级拆分,独立流转 | 各走各的路,发货可按就绪批次 |
| 发货分批要不要 DeliveryPlan 表 | 先不建 | "还剩多少没发"可从 deliveredQty 推算,预先排计划用得少 |
| Order 与 OrderItem 边界 | 整单共享→Order,各行可能不同→OrderItem | 主从结构,行需被独立引用 |

## 十、从现有 schema 演进的路径

每步可独立上线,不破坏现有数据:

1. **先加订购单**:PurchaseRequest + PurchaseRequestItem 上线,Quotation 加 `purchaseRequestId` 可空。老报价单仍能用,新流程走订购单。**风险最低**
2. **报价单多版本**:加 `version` + `superseded` 状态,改 accept/reject 流转。**中等风险**
3. **加生产工单+工序**:ProductionOrder / ProcessStep 上线,把现有 `source='custom'` 的 OrderItem 迁移成挂 ProductionOrder。**最高风险,核心改造**
4. **采购单收窄定位**:加 `purpose` / `processStepId`,新采购单带上下文。**中等风险**
5. **订单状态机重设 + 发货分批校验**:改 status 枚举,加可发货量校验。**需数据迁移旧订单状态**
6. **对账联动订单状态**收尾

> 第 3 步是分水岭。建议先用 1、2 把"订购→多轮报价"链路跑顺(风险低、客户感知最直接),再做最重的生产工单。

## 十一、需要业务确认的边界

影响模型细节,需你校正:

1. **定制加工是全外协,还是部分自制有车间?** 若有自制,ProcessStep 需"工位/设备/操作工/排产"概念,复杂度上升。你提的工序听起来都外协,本方案按全外协设计
2. **工序间是否流转半成品库存?** 车加工完的料回自己仓库再发打丝厂,还是厂对厂直发?若需入半成品库,要加 WIP(在制品)库存模型。本方案默认"厂对厂直发,不入库"
3. **原料采购损耗怎么算成本?** 车 100kg 出 95kg,成本按全价还是按产出摊销?这是成本会计口径,影响 getProfit
4. **分批发货人工还是系统建议?** 本方案默认人工,系统只校验不超发。若要完工自动建发货建议,需加定时任务
5. **客户能看到订购单/报价单状态吗?** 若需客户侧门户,要客户登录态。纯工厂内部用则销售代录

## 十二、与现有代码的对接

本方案是对现有 schema 的**扩展**,不是推翻:

| 现有 | 本方案 |
|------|-------|
| Quotation(无版本) | 加 version + purchaseRequestId |
| Order(status 简单) | 重设状态机为 7 态 |
| OrderItem(source/custom) | 保留,定制件再挂 ProductionOrder |
| PurchaseOrder(孤立) | 加 purpose + processStepId 收窄定位 |
| DeliveryOrder(无超发校验) | 加可发货量校验 |
| Settlement(无状态联动) | 加 paidAmount→completed 联动 |
| (无订购单) | 新增 PurchaseRequest |
| (无生产工序) | 新增 ProductionOrder + ProcessStep |

前四轮代码审查发现的问题(并发超发 #31、对账不联动 #44、入库不校验 #42、成本回填错乱 #43、退货缺失 #46)在本方案中天然得到解决或明确为"已知限制"。

---

> **一句话总结**:现有模型把"定制"这一个最复杂的概念偷懒成了 `source` 标记,导致整条链路的工序、进度、分批、成本都失真。本方案的轴心是**引入 ProductionOrder + ProcessStep**,把定制件当作"一个小型生产项目"来追踪;同时前移加 **PurchaseRequest** 承接客户原始需求、改造 **Quotation** 支持多轮议价,让订单的"来"和"做"都完整。真正的改造是订单之前(订购+多轮报价)和订单条目之内(生产工单+工序),不是推翻现有订单主结构。
