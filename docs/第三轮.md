## 本轮重要结论先说

A 阶段的**框架选择全部正确**(守卫机制、Decimal 工具、env 校验、连接池),但**至少 4 处实施姿势让保护部分或完全失效**:

| # | 做了什么 | 实际效果 |
|---|---------|---------|
| #29 | RolesGuard 全局注册 | ❌ `tenant.controller` 标了 `@Roles('admin')` 却**没带 tenantId 过滤**,admin 能跨租户增删改查**所有**租户 |

## 🔴 P0 — 安全与隔离硬伤(必修)

### 问题 29:tenant 模块完全跨租户操作,admin 可越权访问所有租户

**位置**:`src/modules/tenant/tenant.service.ts` 全部方法

**现状**:
```ts
async findAll(query: QueryTenantDto) {
  const where: any = {};                    // ❌ 无 tenantId 过滤
  // ... 查所有租户
}
async findOne(id: number) {
  return this.prisma.tenant.findUnique({ where: { id } });  // ❌ 不校验
}
async update(id: number, dto: UpdateTenantDto) {
  return this.prisma.tenant.update({ where: { id }, data: dto });  // ❌ 改任意租户
}
async remove(id: number) {
  await this.prisma.tenant.delete({ where: { id } });  // ❌ 删任意租户!
}
```

**问题**:
- tenant.controller 标了 `@Roles('admin')`——这只能保证"是 admin",**不能保证"是本租户的 admin"**
- `findAll` 返回**全平台所有租户**列表,admin 能看到竞品公司名称、联系方式
- `update / remove` 能改/删**任意其他租户**。删租户因外键级联会连带删掉该租户的全部订单/客户/用户——**一次误操作抹掉一家客户的所有数据**
- `TenantContextService` 里甚至预留了 `isSuperAdmin?: boolean` 字段,但从未使用——设计意图是区分"平台超管"和"租户 admin",但代码没实现

**这是多租户 SaaS 最严重的一类漏洞:租户隔离在账户域失效。** 前两轮关注业务模块(order/inbound/settlement)都严格带 `tenantId`,唯独漏了 tenant 自身。

**解法**:明确 tenant 模块的两种语义,二选一:

**方案 A(推荐,单租户自服务)**:租户 admin 只能管理**自己**的租户信息
```ts
async findOne(id: number) {
  const currentTenantId = this.tenantCtx.getTenantIdOrThrow();
  if (id !== currentTenantId) throw new ForbiddenException('无权访问其他租户');
  return this.prisma.tenant.findUnique({ where: { id } });
}
// findAll 直接禁用,或只返回当前租户一条
async findCurrent() {
  const tenantId = this.tenantCtx.getTenantIdOrThrow();
  return this.prisma.tenant.findUnique({ where: { id: tenantId } });
}
```

**方案 B(平台超管视角)**:真正的平台运营后台,需引入 `isSuperAdmin` 角色概念
```ts
// RolesGuard 之前加判断
if (操作目标 tenantId !== 当前 user.tenantId && !user.isSuperAdmin) {
  throw new ForbiddenException();
}
```

> 当前项目是"每家工厂一套部署"的私有化模式,选方案 A。`isSuperAdmin` 字段在单租户阶段用不上,删掉避免误导。

### 问题 30:money.ts 工具被 Number() 预转换抵消,Decimal 精度保护形同虚设

**位置**:`order.service.ts` / `settlement.service.ts` / `purchase.service.ts` 等 5 个 service,共 13+ 处

**现状**:`money.ts` 工具设计是对的——内部 `new Decimal(price)`。但调用方这样写:
```ts
const total = sum(items.map((i: any) => mul(Number(i.price), i.qty)));
//                              ↑            ↑
//                  先 Number(Decimal) 转浮点     再传给 mul
const revenue = mul(Number(item.price), item.qty);
const settledAmount = sum(itemSettlements.map((s) => Number(s.amount)));
```

**问题**:`Number(Decimal)` 一转,PG 返回的字符串/Decimal 对象**已经在 JS 浮点层丢精度**了。`money.ts` 收到的是已经丢精度的 `number`,再用 Decimal 包一层**回不到原始精度**。等于 Decimal 工具白接,前两轮说的"差几分钱"问题**依然存在**。

> 验证:`Decimal('0.1').plus('0.2').toString()` === `'0.3'`,但 `Number(Decimal('0.1'))` 已经是 `0.1` 的浮点近似,`new Decimal(0.1)` 内部存的是 `0.1` 的双精度表示,后续运算精度上限就是 double。

**解法**:money.ts 的入参类型已经支持 `string | Decimal | number`,**调用方直接传原始 Decimal/字符串,不要 Number()**
```ts
// ❌ 现在
mul(Number(i.price), i.qty)
sum(items.map((s) => Number(s.amount)))

// ✅ 改后(Prisma Decimal 对象直接传,或 toString())
mul(i.price, i.qty)                       // i.price 是 Prisma Decimal,money.ts 内部 new Decimal() 能正确处理
sum(items.map((s) => s.amount))
```

需确认 `decimal.js` 能直接吃 Prisma 的 Decimal 对象(它有 `valueOf` 和 `toString`)。若不行,统一 `i.price.toString()` 传字符串——**字符串是精度无损的**。

**配套**:把 `money.ts` 的入参类型收紧,只接受 `string | Decimal`,**禁收 number**——这样调用方传 Number() 会编译报错,从类型层逼出正确姿势:
```ts
type MoneyInput = string | Decimal;  // 不含 number
export function mul(price: MoneyInput, qty: number): number { ... }
```

**工作量**:半小时改调用 + 类型收紧。这是 A 阶段最该收的尾。

### 问题 31:delivery.service.create 无事务且发货超量校验非原子,并发可超发

**位置**:`src/modules/inventory/delivery.service.ts:44-68`

**现状**:
```ts
async create(dto: CreateDeliveryDto) {
  const deliveryNo = await generateNo(this.prisma, 'DO', tenantId);

  // ❌ 先 for 循环 findFirst 校验,不在事务内
  for (const item of dto.items) {
    const orderItem = await this.prisma.orderItem.findFirst({ where: { id: item.orderItemId, tenantId } });
    if (orderItem.deliveredQty + item.qty > orderItem.qty) {
      throw new BadRequestException(`发货数量超过订单数量`);
    }
  }

  // ❌ 再 create,校验和创建之间有时间窗
  return this.prisma.deliveryOrder.create({ data: { ... } });
}
```

**问题**:
1. 校验 (`deliveredQty + qty > qty`) 和创建不在同一事务。两个发货单并发对同一 orderItem,都读到 `deliveredQty=0`、都校验通过、都创建 → **累计发货超过订单数量**
2. `ship` 里是 `deliveredQty: { increment: item.qty }` 无条件加,也不校验,create 阶段漏过的超发会在这里被固化
3. 这与 order.service 的库存原子扣减(已用 `updateMany + gte` 条件更新)形成对比——发货这层漏了同样的加固

**解法**:校验+创建合并进事务,且用"条件更新"做最后防线
```ts
async create(dto: CreateDeliveryDto) {
  const tenantId = this.tenantCtx.getTenantIdOrThrow();
  return this.prisma.$transaction(async (tx) => {
    const deliveryNo = await generateNo(tx as any, 'DO', tenantId);
    for (const item of dto.items) {
      const r = await tx.orderItem.updateMany({
        where: { id: item.orderItemId, tenantId, deliveredQty: { lte: /*qty - item.qty*/ } },
        // 占位:加一个"预占"字段或先查后条件更新
      });
      // 简单做法:先查校验,再依赖 ship 阶段的原子条件更新兜底
    }
    return tx.deliveryOrder.create({ data: { tenantId, deliveryNo, orderId: dto.orderId, items: {...} } });
  });
}

// ship 里把无脑 increment 改成条件更新
for (const item of delivery.items) {
  const orderItem = await tx.orderItem.findFirst({ where: { id: item.orderItemId } });
  const r = await tx.orderItem.updateMany({
    where: { id: item.orderItemId, deliveredQty: { lte: orderItem.qty - item.qty } },
    data: { deliveredQty: { increment: item.qty } },
  });
  if (r.count === 0) throw new BadRequestException(`OrderItem ${item.orderItemId} 发货数量超过订单数量`);
}
```
> ship 是真正落 `deliveredQty` 的地方,把原子校验放这里最可靠,create 只做前置友好校验。

**工作量**:1-2 小时。

### 问题 32:register 开放注册无任何限流/校验,公网可刷量创建垃圾租户

**位置**:`src/modules/auth/auth.controller.ts:14-19` + `auth.service.ts:register`

**现状**:
```ts
@Public()
@Post('register')
register(@Body() dto: RegisterDto) { return this.authService.register(dto); }
```
`register` 直接 `tenant.create` + `user.create`,无任何前置校验。

**问题**:
- 公网任何人可反复 POST 创建租户+管理员,无验证码、无邀请码、无频率限制
- 攻击者脚本跑一晚上能建几万个空租户,塞满 `tenants` 表,影响全平台查询性能(虽然单租户部署不对外,但部署到公网 IP 就暴露)
- 注册接口即使私有化部署,也应有"首次部署后由 init 脚本建首个 admin,后续用户由 admin 在系统内邀请"的语义,而非开放注册

**解法**(按场景选):
- **私有化单租户**:删掉 `/register` 接口,首个 admin 由 `seed.ts` 建。后续用户由 admin 在 `/api/users` 创建(已有 `@Roles('admin')`)
- **若坚持开放注册**:加图形验证码 + IP 限流(每 IP 每小时 N 次)+ 邀请码字段

> 当前项目是单租户私有化,推荐删掉 register,功能和 seed 重复且是安全口子。

### 问题 33:user.update 的 role 越权检查走 service 内 `tenantCtx.getRole()`,与全局 RolesGuard 双轨

**位置**:`src/modules/user/user.service.ts:update`

**现状**:
```ts
@Roles('admin')   // controller 层 RolesGuard 已保证只有 admin 能进
async update(id: number, dto: UpdateUserDto) {
  const currentRole = this.tenantCtx.getRole();
  if (dto.role && currentRole !== 'admin') {     // ❌ 这里又判一次
    throw new BadRequestException('仅管理员可修改角色');
  }
  // ...
}
```

**问题**:
1. controller 已标 `@Roles('admin')`,只有 admin 能进这个方法,`currentRole !== 'admin'` 永远 false → 这段检查是死代码,给人"有保护"的错觉
2. 真正的越权场景没覆盖:admin 把**别的租户**的 userId 传进来,`updateMany({ where: { id, tenantId } })` 因 tenantId 来自 context 是 admin 自己的租户,传别人的 id 改不到——**这点安全**(隔离有效),但前提是 tenantId 取自 context 而非参数,确认无误
3. `UpdateUserDto` 含 `role` 字段,admin 能改任意用户的 role(包括把自己降级成 staff 后锁死自己)。虽是 admin 自找,但应有"不能改自己 role"或"最后一个 admin 不能降级"的保护

**解法**:
- 删掉 service 内的 `currentRole` 死代码判断(已被 RolesGuard 覆盖)
- 加"admin 不能降级自己"+ "租户至少保留一个 admin"的人性化保护
```ts
async update(id: number, dto: UpdateUserDto) {
  const tenantId = this.tenantCtx.getTenantIdOrThrow();
  const userId = this.tenantCtx.getUserId();

  if (dto.role && dto.role !== 'admin' && id === userId) {
    throw new BadRequestException('不能降级自己的管理员角色');
  }

  // 若降级后无 admin,拒绝
  if (dto.role && dto.role !== 'admin') {
    const target = await this.prisma.user.findFirst({ where: { id, tenantId } });
    if (target?.role === 'admin') {
      const adminCount = await this.prisma.user.count({ where: { tenantId, role: 'admin' } });
      if (adminCount <= 1) throw new BadRequestException('租户至少需保留一个管理员');
    }
  }
  // ... 原更新逻辑
}
```

### 问题 34:getProfit 嵌套 include 同步计算,数据量上来必慢

**位置**:`src/modules/order/order.service.ts:getProfit`

**现状**:
```ts
const order = await this.prisma.order.findFirst({
  where: { id: orderId, tenantId },
  include: { items: { include: { purchaseOrder: { include: { items: true } } } } },
});
// 然后 JS 层 forEach 算每个 item,再 find purchaseOrder.items.find(poi => poi.skuCode === item.skuCode)
```

**问题**:
- 三层嵌套 include,一次拉回订单+条目+采购单+采购条目全量数据
- 对每个 custom 条目用 `purchaseOrder.items.find(skuCode === ...)` 在内存里线性查找,N 个条目 × M 个采购条目 = O(N×M)
- 前两轮关注的都是"写"路径,这里是"读"路径的性能债。订单 50 项、采购单各 10 项时还好;千项级订单(虽少见)会卡
- 更深层:利润是高频查询(销售每开一单都想看利润),**实时算**迟早成瓶颈

**解法**(分级):
- 短期(10 分钟):`purchaseOrder.items.find` 改用预建 `Map`,O(1) 查找
```ts
const poItemMap = new Map(order.items.flatMap(i =>
  i.purchaseOrder ? i.purchaseOrder.items.map(pi => [pi.skuCode, pi]) : []
));
// 用 poItemMap.get(item.skuCode)
```
- 中期:SKU 层维护 `lastCostPrice`,下单/入库时更新,`getProfit` 直接读无需回查采购单
- 长期(到了 A+ 阶段):利润预计算 + 物化视图,报表查询走汇总表

> 短期改动顺手就能做,收益明显。

### 问题 35:@nestjs/config 装了但未启用,env 校验是手动 validateEnv(),配置注入方式不统一

**位置**:`package.json` 有 `@nestjs/config` 依赖,但 `app.module.ts` 未 import `ConfigModule`,`main.ts` 手动调 `validateEnv()`

**现状**:
- `main.ts:9` 启动时调 `validateEnv()` 校验 ✓
- `auth.module.ts:13` `JwtModule.register({ secret: process.env.JWT_SECRET! })` 直接读 `process.env` ✗
- `prisma.service.ts` `process.env.DATABASE_URL` 直接读 ✗
- 全项目散落 `process.env.XXX`,无统一配置服务

**问题**:
- `@nestjs/config` 装了却没用,依赖白装
- `process.env.JWT_SECRET!` 用非空断言 `!` 绕过类型,虽 `validateEnv` 保证了运行时存在,但类型层不安全
- 无法对配置做单元测试(需 mock process.env)
- 若未来加 `ConfigService.get('jwt.secret')` 的方式,现有直接读 `process.env` 的地方要逐个改

**解法**:统一用 `@nestjs/config` + `ConfigService`
```ts
// app.module.ts
import { ConfigModule } from '@nestjs/config';
@Module({
  imports: [
    ConfigModule.forRoot({
      isGlobal: true,
      validate: (env) => plainToInstance(EnvConfig, env, { enableImplicitConversion: true }),
      validateOptions: { skipMissingProperties: false },
    }),
    // ...
  ],
})

// auth.module.ts
JwtModule.registerAsync({
  inject: [ConfigService],
  useFactory: (config: ConfigService) => ({
    secret: config.get<string>('JWT_SECRET'),
    signOptions: { expiresIn: '24h' },
  }),
})

// prisma.service.ts
constructor(private config: ConfigService) {
  const pool = new Pool({ connectionString: config.get<string>('DATABASE_URL')! });
}
```
> 这样 main.ts 的手动 `validateEnv()` 可移除,ConfigModule 在 `forRoot` 时自动校验,配置来源单一。

**工作量**:1 小时。收益:配置注入一致、可测试、类型安全。

### 问题 36:seed.ts 不完全幂等,部分 upsert 部分 findFirst+create

**位置**:`src/prisma/seed.ts`

**现状**:
```ts
// admin 用了 upsert ✓
await prisma.user.upsert({ where: { tenantId_username: {...} }, update: {}, create: {...} });

// 但很多业务数据是 findFirst + create ✗
let tenant = await prisma.tenant.findFirst({ where: { name: '紧固件工厂' } });
if (!tenant) { tenant = await prisma.tenant.create({...}); }
```

**问题**:`grep -c "upsert\|create" seed.ts` 显示 9 处混合。`findFirst + create` 模式在**并发**或**部分失败重跑**时不安全——两个 seed 进程同时跑可能都查不到、都创建,违反唯一约束报错。虽 seed 一般单进程跑,但 CI/容器重启时可能并发。

**解法**:全部改 upsert,按唯一键
```ts
await prisma.tenant.upsert({
  where: { name: '紧固件工厂' },  // name 需加 @unique,或用其他唯一键
  update: { contact: '李总', phone: '13800001111' },  // 重跑时更新(可选)
  create: { name: '紧固件工厂', contact: '李总', phone: '13800001111' },
});
```
> tenant.name 当前无 @unique,要么加约束,要么接受 findFirst+create 的单进程假设并在文档注明"禁止并发 seed"。

### 问题 37:JWT refresh 无 token 吊销机制,改密码/封禁用户后旧 token 仍有效

**位置**:`auth.service.ts:refresh` + `jwt.strategy.ts:validate`

**现状**:
- token 有效期 24h,期间无法吊销
- `validate` 只校验签名,不查用户当前状态(是否被禁用、密码是否已改)
- admin 封禁一个用户(改 role 或删除),该用户的 token 在 24h 内仍有权操作

**问题**:这是 JWT 的固有特性,但在 ERP 场景(财务敏感)有风险:
- 离职员工 24h 内还能操作系统
- 密码泄露后改密码,攻击者的旧 token 仍有效

**解法**(分级):
- 短期(单租户,可接受)`validate` 里查一次用户是否存在且 role 未变:
```ts
async validate(payload: JwtPayload) {
  const user = await this.prisma.user.findFirst({
    where: { id: payload.sub, tenantId: payload.tenantId },
    select: { id: true, role: true },
  });
  if (!user) throw new UnauthorizedException('用户不存在或已禁用');
  return { userId: user.id, tenantId: payload.tenantId, role: user.role };
}
```
> 代价:每次请求多一次轻量查询(可加内存缓存 30s)。收益:封禁/删除即时生效。
- 中长期:引入 refresh token + access token 双 token,access 短期(15min),refresh 长期可吊销,存 DB。

**工作量**:短期方案 1 小时。

### 问题 38:env 校验与 JwtStrategy 校验重复,且 JWT_SECRET 校验逻辑分散三处

**位置**:`env.validation.ts`、`jwt.strategy.ts:16-18`、`auth.module.ts:13`

**现状**:JWT_SECRET 的存在性和长度校验出现在:
1. `env.validation.ts` 的 `@MinLength(32)` —— 启动时
2. `jwt.strategy.ts` 构造函数 `if (!secret || secret.length < 32) throw` —— 模块初始化时
3. `auth.module.ts` `process.env.JWT_SECRET!` —— 直接用

## 🟢 P3 — 代码质量与边界

### 问题 39:RolesGuard 对 user 为 undefined 的场景无显式处理

**位置**:`src/common/guards/roles.guard.ts`

**现状**:
```ts
const { user } = context.switchToHttp().getRequest();
return requiredRoles.includes(user?.role);  // user 可能为 undefined
```

**问题**:`@Public()` 路由 JwtAuthGuard 跳过,`req.user` 为 undefined。若一个 `@Public` 路由**不小心**也标了 `@Roles`,`user?.role` 是 `undefined`,`requiredRoles.includes(undefined)` 返回 false → 拒绝。这反而安全(拒绝优于放行),但报错信息模糊。生产中 `@Public` + `@Roles` 共存是配置错误,应有更早的提示。

**解法**:加开发期断言,配置错误直接报清楚
```ts
canActivate(context: ExecutionContext): boolean {
  const requiredRoles = this.reflector.getAllAndOverride(ROLES_KEY, [context.getHandler(), context.getClass()]);
  if (!requiredRoles || requiredRoles.length === 0) return true;

  const { user } = context.switchToHttp().getRequest();
  if (!user) {
    // 标了 @Roles 但 req.user 为空 = 守卫顺序配置错误
    throw new UnauthorizedException('接口需要登录但用户上下文为空,检查守卫顺序');
  }
  return requiredRoles.includes(user.role);
}
```

### 问题 40:ValidationPipe 缺 forbidNonWhitelisted,未知字段被静默丢弃而非报错

**位置**:`src/main.ts:13-18`

**现状**:
```ts
new ValidationPipe({
  whitelist: true,                    // ✓ 已开:未知字段被剥离
  transform: true,                    // ✓
  transformOptions: { enableImplicitConversion: true },
  // ❌ 缺 forbidNonWhitelisted: true
});
```

**问题**:`whitelist: true` 把未知字段**静默剥离**。前端传错字段名(如 `customerdId` 拼错)不报错,请求照常处理,数据却没了那个字段——后端"成功"返回但前端纳闷为什么没生效,调试困难。

**解法**:`forbidNonWhitelisted: true`,未知字段直接 400 报错,前端立刻发现拼写错误。
